# CI and release operation

The workflows are implemented and locally linted/tested. Remote execution is not yet verified: this checkout has no commits or Git remote, and the current GitHub credentials could not resolve the configured repository `jmylchreest/obs-wow-companion`.

## Workflows

| Workflow | Trigger | What must pass |
| --- | --- | --- |
| CI | PR, push to main, manual, weekly | Reusable quality and package workflows |
| Quality | Called by CI or Release | Rust 1.95 formatting, strict Clippy, nextest and doc tests on Ubuntu 24.04 / Windows 2025; docs, cargo-deny, notice consistency, actionlint and release-boundary tests |
| Packages | Called after quality succeeds | Native Linux GNU / Windows MSVC archives, SHA-256 and binary-version checks, required docs/templates/notices, packaged service/media tests on both OSes; Linux native window, WebKit playback and process-crash recovery |
| Packages: bundle/installers | After both native archive jobs succeed | cargo-dist shell/PowerShell installers and source archive; embedded archive checksums; private installation and installed-service tests on both OSes |
| OBS integration | Manual and weekly | Official OBS Ubuntu PPA, isolated virtual display/profile, recording/splits and manual/log-triggered two-track exports; records installed OBS version |
| Prepare release PR | Manual on main | release-plz 0.4.1 prepares version/changelog PR only; no tag, registry publication or GitHub release |
| Release | Push of `v…` tag | Exact tag/workspace-version agreement, quality, both packages, bundle and installer tests; only then publish |

OBS integration tracks the official PPA as a compatibility canary and is separate from the reproducible application checks. A newly published OBS version does not automatically become a supported version. Its installation source follows the [official OBS Ubuntu instructions](https://obsproject.com/kb/linux-installation).

The parser benchmark is collected on Linux as evidence, without a noisy timing threshold on shared runners. Nextest JUnit reports, Criterion output, screenshots and diagnostic logs are retained for 14 days. Every CI run produces a downloadable `release-bundle` when package verification succeeds; CI does not publish it.

## Publication boundary

All ordinary jobs have read-only repository permission. Only the release publication job and explicitly invoked release-PR job have write permission. External actions use full commit hashes, checkout does not retain credentials, and pull requests run through `pull_request`, never `pull_request_target`.

The release job depends directly on successful validation, quality and packages. It has no `always()` override that would allow failed/skipped prerequisites to publish. Regression tests check this dependency graph and reject corrupt archives, incomplete platform bundles and mismatched version tags. Publish rechecks every bundled artifact hash and requires the Git tag to exist. Prerelease versions are marked as prereleases.

The workflows are maintained in this repository rather than regenerated by cargo-dist. `allow-dirty = ["ci"]` disables only cargo-dist's generated-workflow comparison; it does not bypass compilation, tests or artifact verification. Keep the package configuration in `dist-workspace.toml`, and validate workflow edits with actionlint and the Python tests.

## Repository activation

1. Confirm the GitHub repository destination and access. If its URL differs, update Cargo repository metadata and release URL verification in `scripts/ci-tools.py` before packaging.
2. Commit the source and push it to the intended repository. Enable GitHub Actions. The first main push runs CI; a manual CI run is also available.
3. Review both OS results and download the reports/artifacts. Configure branch protection using the successful checks shown by GitHub; require quality and package verification before merging.
4. To use release preparation, allow Actions to create pull requests in repository settings. The default `GITHUB_TOKEN` can create a PR, but bot-created PRs do not automatically trigger another workflow. Run CI manually on that branch, or provide `RELEASE_PR_TOKEN` from a suitably scoped GitHub App/token if automatic PR CI is needed. See [release-plz setup](https://release-plz.dev/docs/github/quickstart).
5. After all [release qualification gates](validation.md) pass, merge reviewed version/changelog changes and push the matching `vVERSION` tag. A tag is the publication trigger; a manual CI run or release-PR preparation does not publish.

No crates.io token is needed. OBS and FFmpeg remain separately installed runtime dependencies. CI installs FFmpeg on both runners; this does not bundle it into the app.

## Local verification

Run `python3 scripts/ci-tools.py actionlint`, then `python3 -m unittest discover -s scripts -p 'test_ci*.py'` with PyYAML 6.0.3 installed. Run `cargo nextest run --workspace --locked --profile ci` to reproduce JUnit output.

For a local archive, set `DIST_TARGET` to its Rust target and run `python3 scripts/ci-tools.py package target/distrib`. The helper validates the checksum, extracts into a private directory, checks contents and runs the binary. In Actions it sets `OWC_BINARY` for subsequent probes. `scripts/service-smoke.py` works on both target OSes; native WebView2 interaction still needs separate Windows qualification.

The installer smoke test serves artifacts from a private loopback HTTP server, uses cargo-dist's unmanaged temporary installation setting and disables PATH changes. It does not alter the user's normal installation. Passing it proves the install mechanism and local service; it does not prove game capture or that every clean machine has the required system libraries.
